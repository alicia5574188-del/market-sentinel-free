# Resonance 必要能力兼容基线

本文件是所有后续 UI、策略、架构和品牌重构的长期回归基线。

**Must-Keep 保的是用户和系统真正依赖的能力，不是旧页面、旧按钮、旧组件或旧实现。**

任何旧功能准备恢复前，必须先与当前 `main`、当前产品架构和实际运行链路做兼容性审查。不能因为“以前有”就原样搬回。

## 1. 恢复前兼容性审查

每一个候选恢复项必须先归类为以下四种之一：

1. **保留现状**：当前版本已经提供同等或更好的能力，不恢复旧实现。
2. **补缺 / 改造**：当前能力不完整，只补真正缺失的信息或操作，并沿用现有数据源和安全边界。
3. **重新实现**：旧能力仍有价值，但旧实现与当前架构冲突；只保留业务目标，用当前架构重新实现。
4. **淘汰**：旧功能已重复、已被替代、价值不足，或恢复会明显增加复杂度、请求量和故障面，不再恢复。

审查时至少回答：

- 当前版本是否已经存在同等能力？
- 当前版本是否已经有更好的替代路径？
- 是否会形成重复入口、重复状态源、重复业务逻辑或重复危险操作？
- 是否会新增高频轮询、Gate 前台请求、客户端计算或新的后台权威生产者？
- 是否会改变 Scanner、策略权威、风险边界、D1 历史、Gate 执行或凭据安全模型？
- 辅助接口失败时，是否仍能保证主页面和核心交易链路正常？
- 这个能力对交易、安全、诊断、复盘或账户操作是否仍有明确价值？

没有通过兼容性审查的旧功能不得进入恢复实现。

## 2. 稳定性优先原则

恢复或保留能力时，不得重新引入页面黑屏、频繁 503、前台 Gate 扇出、接口互相拖累等旧问题。

必须遵守：

- 后台 MarketScanner 继续作为生产市场数据的权威生产者；普通页面读取不能重新变成 Gate 全市场计算生产者。
- 辅助功能接口失败只能局部降级，不能让主页面、Scanner、Position Monitor、Live Coordinator 或交易执行失效。
- 账户、通知、安全审计、复盘详情等操作型功能优先按需读取，不得仅为展示它们新增高频定时轮询。
- Mutation 不得自动重试；实盘写操作继续由既有安全边界负责。
- PWA / Service Worker 不得用缓存 App Shell 冒充 API JSON。
- 不为了恢复 UI 能力修改策略权威、风险规则、D1 历史或 Gate 凭据。
- 同一个高风险操作默认只保留一个明确的主执行入口；其他页面可以导航过去，但不要重复堆放危险按钮。

## 3. 必须持续具备的能力

### 模拟账户

系统必须能让操作者看到当前模拟本金 / 本轮起始资金、权益、已用保证金和可用资金，并能在安全条件满足时重新开始模拟资金曲线。

资金重置必须满足：

- 不删除历史交易与学习数据。
- 有模拟持仓时不得重置资金 epoch。
- 操作入口必须可发现，但不要求出现在多个页面。

### 模拟交易与复盘

操作者必须能理解一笔交易“为什么进、怎么保护、结果怎样、哪里做得好或差”。必要信息包括：

- 方向、进场、当前 / 出场价格。
- 原始止损与当前保护价。
- TP1、TP2、TP1 是否已经触发。
- 杠杆、隔离保证金、名义仓位、计划风险。
- 成本后的 TP2 预计收益。
- MFE / MAE、退出效率、退出后观察与反事实复盘。
- 交易策略 / 打法、进入理由、退出理由。

这些信息可以折叠或按需加载，不要求恢复旧版卡片布局。

### Gate 实盘

必须持续具备以下能力：

- 清楚区分公开市场可用、API 已配置、API 已验证、Auto Live 状态、风险锁和 API 异常。
- Gate 凭据可以安全配置、更换和删除；Secret 不回显。
- Auto Live 总开关和立即对账。
- 风险锁 / 实盘资格及原因可见。
- 活动真实订单能看到必要保护状态和策略来源。
- Emergency Stop 必须始终可达，并保持移动端可可靠触发。
- 必要的实盘安全审计可按需查看。

不得为了“恢复旧实盘页”创建第二套 Live 状态源、第二套 Gate 请求链路或第二套风控逻辑。

### 账户

必须有当前登录账户、Owner / 只读成员身份和退出登录能力。具体入口可以与设置或操作面板合并，只要清楚可达。

### Web Push

必须保留开启、关闭和测试推送链路的能力。推送管理应独立失败、按需执行，不得影响主页面；iPhone 继续遵循 Safari 添加到主屏幕后的 PWA 推送能力。

### 后台与诊断

必须能诊断 Scanner 和持仓管理是否正常，包括必要的最近成功时间、阶段 / 错误 / 新鲜度等信息。页面关闭或 iPhone 锁屏后，服务器后台扫描与持仓保护继续运行。

### 导航与可发现性

核心能力必须有合理可达入口，但“可达”不等于“每个页面都放一个按钮”。

允许：

- 折叠、移动、合并到设置或操作面板。
- 从首页提供导航入口，再在设置页执行危险操作。
- 复用当前版本已经存在的入口，而不是复制旧入口。

不允许：

- 为了所谓简洁把必要能力彻底删除。
- 为了所谓恢复把同一高风险操作到处复制。
- 因为旧版测试写死某个按钮或页面位置，就阻碍新的等价实现。

## 4. 回归测试保护什么

回归测试优先保护**行为和安全约束**，而不是旧 DOM 文案或旧组件名字。

可以使用关键文案 / 路由断言保证能力仍可达，但测试不得无理由要求：

- 同一按钮必须出现两次。
- 某能力必须待在旧页面。
- 已被新架构替代的旧组件必须继续存在。
- 已淘汰的旧请求链路重新加入。

对于危险操作，测试应优先验证：入口存在、限制条件存在、后端路由存在、不会重复暴露不必要的执行入口。

## 5. 后续更新的强制检查

任何影响 `app/page.tsx`、主导航、设置页、交易页、实盘页、PWA 或产品架构的 PR，在完成前必须回答：

1. 新功能是否正常？
2. 必要能力是否仍然可达？
3. 候选旧功能是否做过“现版本重复 / 替代 / 冲突 / 价值”检查？
4. 是否引入重复入口、重复状态源或重复业务逻辑？
5. 是否新增了不必要的轮询或 Gate 前台请求？
6. 任一辅助接口失败时是否仍能保持主页面可用？
7. Emergency Stop、Auto Live、保护与风控是否仍保持原有安全边界？
8. 是否跑过 capability-preservation / UI / build / risk regression tests？

只要上述任一项不满足，该更新不得视为完成。
